## 1. What this is

GlucoLens is a clinical-grade blood glucose tracking mobile app built with Expo/React Native. A patient completes an onboarding profile (name, age, gender, diabetes condition), logs glucose readings with context (fasting, before/after meal, bedtime, random), and the app classifies each reading against ADA 2024 condition-specific reference ranges, tracks trends, pairs before/after-meal readings to show meal response, estimates HbA1c, and produces a doctor-ready "Visit Summary." Data is stored locally in SQLite and synced to a Supabase Postgres backend with per-user row-level security.

- **Product name:** GlucoLens
- **package.json name:** `glucolens-fresh`
- **Bundle ID (iOS + Android):** `com.glucolens.app`
- **Version:** 1.0.0
- **URL scheme:** `glucolens://` (declared in app.json; not currently used by any deep-link flow)

## 8. Local database — `src/db/database.ts`

Uses `expo-sqlite`'s synchronous API (`openDatabaseSync`, `execSync`, `runSync`, `getFirstSync`, `getAllSync`). Singleton connection via `getDb()`.

**Schema**, created in `initializeDatabase()` (called once, in the root layout's `useEffect`):
```sql
CREATE TABLE IF NOT EXISTS patients (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, age INTEGER NOT NULL,
  gender TEXT NOT NULL, condition TEXT NOT NULL, weight REAL, height REAL,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS glucose_readings (
  id TEXT PRIMARY KEY, patient_id TEXT NOT NULL, value REAL NOT NULL,
  unit TEXT NOT NULL DEFAULT 'mg/dL', context TEXT NOT NULL, notes TEXT,
  recorded_at TEXT NOT NULL, created_at TEXT NOT NULL,
  FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_readings_patient ON glucose_readings(patient_id, recorded_at DESC);
```
No migration framework — schema evolution would mean hand-adding more `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE` statements here.

**Functions**: `getDb()`, `savePatient` (upsert via `INSERT OR REPLACE`), `getPatient(id)`, `getAllPatients()` (all rows, `ORDER BY created_at DESC` — defined but unused, app only ever has one active patient), `saveReading` (upsert), `getReadings(patientId, days=30)` (filters `recorded_at >= cutoff`, `ORDER BY recorded_at DESC`), `deleteReading(id)` (hard delete — defined but never called from any screen), private row-mappers `mapRowToPatient`/`mapRowToReading` (convert SQL `null` → TS `undefined` for optional fields).

## 10. Business logic — `src/utils/helpers.ts`

- `generateId()` — `${Date.now()}-${random base36}`. Not a UUID; fine for local SQLite ids (Postgres generates its own separate UUIDs for the same conceptual rows on the cloud side).
- `mgToMmol(mg)` = round(mg/18.0182, 1dp); `mmolToMg(mmol)` = round(mmol×18.0182).
- `getRangeForContext(context, condition)` — picks the right `GlucoseRange` sub-object (fasting/postMeal/bedtime/random — `before_meal` and `random` both map to the `random` range).
- `classifyGlucose(value, context, condition)`:
  1. `< STATUS_THRESHOLDS.critical_low (54)` → `critical`
  2. `< range.low` → `low`
  3. `<= range.high` → `normal`
  4. `>= STATUS_THRESHOLDS.critical_high (300)` → `critical`
  5. `range.high < value < range.high × 1.3` → `elevated`
  6. else → `high`
- `enrichReading(reading, condition)` — attaches `status` + human label.
- `computeStats(readings, condition)` — average/min/max (rounded), `timeInRange` = % classified `normal`, naive `trend`: splits readings in half (list is DESC-sorted, so "first half" = more recent), `improving` if recent avg is >5 lower than older avg, `worsening` if >5 higher, else `stable`.
- `toChartData(readings, condition)` — ascending-sorted `{value, label:'MMM d', date, context, status}[]`.
- `formatDate` (`MMM d, yyyy`), `formatDateTime` (`MMM d · h:mm a`), `formatRelative` (date-fns relative), `formatGlucose(value, unit)`, `formatGlucoseAmount(amountMgDl, unit)` (unit-aware magnitude formatter, always non-negative — sign handled by the caller), `formatRange(low, high, unit)`, `formatElapsedMinutes(minutes)` (`"45m"` / `"2h"` / `"2h 15m"`), `contextLabel(context)`.

## 11. Meal pairing — `src/utils/mealPairing.ts`

Matches `before_meal` readings to the nearest-appropriate `after_meal` reading, so the app can show "before → after" meal response.

- `PAIR_TARGET_MINUTES` = `APP_CONFIG.postMealMinutes` (120) — the ADA-recommended ~2h postprandial check window; this is the *one place* that constant actually drives behavior now.
- `PAIR_MIN_WINDOW_MINUTES` = 30 — below this, a pair is still shown but framed as "early" (glucose likely still rising), not a finished verdict.
- `PAIR_MAX_WINDOW_MINUTES` = 240 — above this, no pairing at all (more likely the next meal's before-reading).
- `maturityFor(elapsedMinutes)` → `'early' | 'ideal'`.
- `pairMealReadings(readings, condition)` — processes before-meal readings earliest-first, greedily claims the closest-to-target unclaimed same-day after-meal reading within the eligible window (so an after-meal reading is never reused across two different meals). Returns `MealPair[]` sorted most-recent-first, each with `elapsedMinutes`, signed `deltaMgDl`, `direction` ('increase'/'decrease'/'unchanged'), and `maturity`.
- `findBestBeforeMealMatch(readings, condition, afterMealAt)` — for a not-yet-saved after-meal reading being composed live (used by the Log screen's real-time pairing preview), finds the best unclaimed before-meal candidate from today.

## 12. Visit summary composition — `src/utils/visitSummary.ts`

Builds everything the Visit Summary screen renders, over a 30-day window.

- `computeContextInsights(readings, condition)` — per-context (fasting/before_meal/after_meal/bedtime/random) average, % in range, count, and the status classification of that average.
- `getNotableReadings(readings, condition, {limit=5, maxPerDay=2})` — ranks non-normal readings by a `severityScore` (boundary distance × 1.5 if low, × 2.0 if critical), caps at 2 per calendar day so one bad day doesn't dominate the list, returns top 5 with signed `deviationMgDl`.
- `detectPatternFlags(contextInsights, stats, hypoCount, condition)` — up to 3 synthesized sentences: flags any hypo events (severity `critical`), flags any context with ≥5 readings and <60% in-range (severity `warning`, states how far over/under target on average), or if nothing's wrong, a single "good" sentence citing time-in-range.
- `computeVisitSummary(patient, readings, windowDays=30)` — top-level composer returning stats, HbA1c estimate, chart data, context insights, pattern flags, notable readings, target ranges, and hypo count.

## 13. Supabase client & cloud sync

### `src/lib/supabase.ts`
- `SecureStoreAdapter` — custom storage adapter for Supabase's auth persistence: `expo-secure-store` (encrypted Keychain/Keystore) on native, `localStorage` on web.
- Reads `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` from `process.env`; if either is missing, logs a `console.warn` with setup instructions but does **not** throw — the client is still constructed against an empty URL, so calls would fail at request time instead of at startup.
- `createClient(..., { auth: { storage: SecureStoreAdapter, autoRefreshToken: true, persistSession: true, detectSessionInUrl: false } })`.

### `src/lib/sync.ts`
- `syncPatientToCloud(patient)` — upserts into `patients` with `onConflict: 'user_id'`. Called once, from onboarding's `handleFinish`.
- `fetchPatientFromCloud()` — `select('*').single()` on `patients` (RLS scopes it to the caller), maps and persists locally via `savePatient`.
- `syncReadingsToCloud(readings[])` — bulk-inserts readings. **DEAD** — defined but never called from anywhere in the app. This means readings logged in the Log screen only ever exist locally; they're never pushed to Supabase (see §14).
- `fetchReadingsFromCloud(patientId, days=30)` — pulls readings since cutoff, maps, persists each locally via `saveReading`.
- `syncOnLogin()` — orchestrator: fetch patient, then (if found) fetch last 90 days of readings. Called from `app/index.tsx` (session restore) and `app/(auth)/login.tsx` (post sign-in).

### `supabase/schema.sql`
Run manually via the Supabase SQL editor (not migration-tooled).
- `uuid-ossp` extension for `uuid_generate_v4()`.
- **`public.patients`**: `id UUID PK`, `user_id UUID NOT NULL REFERENCES auth.users ON DELETE CASCADE`, `name`, `age INTEGER CHECK (0 < age < 150)`, `gender CHECK IN (male/female/other)`, `condition CHECK IN (4 values)`, `weight`, `height`, `created_at`/`updated_at TIMESTAMPTZ`.
- **`public.glucose_readings`**: `id UUID PK`, `patient_id UUID REFERENCES patients ON DELETE CASCADE`, `user_id UUID REFERENCES auth.users ON DELETE CASCADE`, `value REAL CHECK (0 < value < 1000)`, `unit CHECK IN (mg/dL, mmol/L)`, `context CHECK IN (5 values)`, `notes`, `recorded_at`/`created_at TIMESTAMPTZ`.
- **`idx_patients_user_id` is a `UNIQUE` index** on `patients(user_id)` — this correctly satisfies the `onConflict: 'user_id'` upsert in `syncPatientToCloud`.
- `idx_readings_patient_id (patient_id, recorded_at DESC)`, `idx_readings_user_id (user_id, recorded_at DESC)`.
- `update_updated_at()` plpgsql trigger function, bound `BEFORE UPDATE` on `patients` only.
- **RLS enabled on both tables**, each with a single `FOR ALL USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)` policy — full per-user row isolation, no admin bypass.

## 15. Dev tooling — `scripts/seed-test-data.ts`

A standalone Node/tsx CLI script (run via `npx tsx scripts/seed-test-data.ts`, **not** meant to be run by an AI tool call — it prompts interactively for your GlucoLens email/password and never persists them). It:
1. Loads `.env` manually (reimplements simple dotenv parsing).
2. Constructs a Supabase client with a `ws` WebSocket polyfill (needed because plain Node lacks a native `WebSocket`, which `supabase-js`'s realtime client requires just to construct, even though this script never uses realtime).
3. Signs in, finds the authenticated user's patient row.
4. Inserts a hand-crafted 30-day spread of ~25 readings designed to exercise specific app behaviors: mostly-normal fasting readings, a consistently-high after-meal pattern (to trigger the "runs high" pattern flag), normal bedtime readings, two separate hypo events, one severe critical-low (to confirm it ranks #1 in Notable Readings), and a same-day 3-reading cluster (to exercise the notable-readings 2-per-day cap).

This exists because the in-app Log screen always timestamps `new Date()` — there's no way to backdate a reading from the UI, so this script is the only way to get realistic date-spread test data for Trends/Visit Summary.

## 16. Known issues / open gaps

Two issues flagged in earlier review passes are **now resolved** in the current code:
- ✅ `trends.tsx` previously used an invalid `minValue` prop on `LineChart` — no longer present; `tsc --noEmit` is currently clean across the whole project.
- ✅ `patients.user_id` previously lacked a `UNIQUE` constraint while `syncPatientToCloud` upserted with `onConflict: 'user_id'` — `schema.sql` now defines `idx_patients_user_id` as `UNIQUE`.
- ✅ The mmol/L toggle on Profile was previously local-only/cosmetic — it's now backed by persisted, app-wide state (`useAppStore.unit`).
- ✅ `.env` was previously not gitignored — it now is.

**Still open:**
1. **Readings never sync to the cloud.** `syncReadingsToCloud` exists but nothing calls it. `addReading`/`removeReading` only touch local SQLite. Logged data survives only on-device until some future code path pushes it.
2. **Password reset has no `redirectTo`.** `resetPasswordForEmail(email)` is called with no redirect target, so the emailed link likely can't deep-link back into the app via the declared `glucolens://` scheme.
3. **No edit/delete UI for readings**, despite `removeReading` existing in the store and `deleteReading` in the DB layer.
4. **No edit-profile UI**, despite `updatePatient` existing in the store.
5. **`isOnboarded`/`setOnboarded`/`APP_CONFIG.onboardingKey`** (AsyncStorage-backed) are fully implemented but orphaned — nothing reads or writes them; onboarding-completion is actually tracked by "does `activePatient` exist."
6. **`weight`/`height`** fields on `PatientProfile` are never collected or displayed anywhere.
7. **No multi-patient/caregiver mode** — `getAllPatients()` exists but is unused; the app assumes exactly one patient per account.
8. **`App.tsx`** is dead — the unused default Expo template. Real entry is `index.ts` → `expo-router/entry`.
9. **The entire legacy `COLORS`/`SPACING`/`RADIUS`/`FONT`/`SHADOW` block in `src/constants/index.ts`** (plus `STATUS_COLORS`/`STATUS_BG_COLORS`/`STATUS_TEXT_COLORS`) is dead code, fully superseded by `theme.ts`.
10. **`CONTEXT_ICONS`, `APP_CONFIG.chartDaysDefault`, `STATUS_THRESHOLDS.low`, `useAppStore.isLoading`/`setLoading`** are all declared but unused.
11. **tsconfig path aliases** `@components/*`, `@hooks/*`, `@store/*`, `@types/*`, `@utils/*`, `@db/*` are declared but never used (everything imports via `@/*`); `@hooks/*` points at a nonexistent directory.
12. **No tests, no CI, no `eas.json`** — nothing in the repo currently supports an automated build/release pipeline.
13. **No error boundary or crash reporting** — an uncaught error in `initializeDatabase()` or auth `initialize()` has nothing catching it.
14. **Onboarding's "AI-powered" language was previously a concern in earlier review passes and has since been removed** — the current 3 feature bullets ("Personalized ADA 2024 reference ranges," "Time-in-range and HbA1c trends," "Doctor-ready visit summaries") now all describe real, shipped functionality.
